## 已确认问题

P2表示应排进近期修复的局部问题；P3表示影响较小的边界或说明问题。以下不是八项全局故障，优先级也不等于发生概率。

### A01 · P2 · 连续选技会消费尚未显示的新卡

- 位置：`dist/js/overlays.js:165`、`dist/js/hud.js:199`、`dist/js/app.js:97`。
- 条件：积压至少两次待选，在下一次100ms HUD刷新前再次点击旧卡。
- 证据：固定种子12345，显示第一张`power`，待选2次；第一次点击后后台第一项已经重抽为`precision`，HTML仍未变化；再次点旧第一张后获得`power:1, precision:1`，待选归零。
- 原因：按钮绑定索引，处理器读取最新的`player.choices[index]`；选择立即重抽，但可见卡片延迟刷新。
- 建议：卡片绑定技能ID和选项版本；拒绝过期事件，并在选中后立即更新或禁用旧卡。选技不停战可以保留。补充连续点击、数字键与鼠标交替、待选队列多个节点的真实入口用例。
- 验证边界：用现有DOM夹具加载真实`app.js`及绑定复现，预先设置积压选择，没有把它冒充自然完整真人对局。

### A02 · P2 · 帮助层没有隔离焦点和恢复操作

- 位置：`dist/js/overlays.js:151`、`:177`、`:183`；`dist/index.html:47`。
- 浏览器复现：开局→点“玩法指南”→Tab→Enter。打开时焦点仍在`help-button`，Tab直接到背景`pause-button`，Enter恢复对局，帮助仍可见，时钟从00:08推进到00:22。
- 影响：阅读指南时可在战场被遮挡的情况下恢复模拟并受伤；重复打开帮助也会覆盖此前暂停状态。
- 建议：打开帮助时移入并约束焦点，背景设置不可交互，关闭后恢复焦点；帮助显示期间禁止其他入口恢复对局；重复打开保持幂等。添加“已暂停/未暂停打开帮助、重复打开、Tab循环、Esc关闭”的用例。

### A03 · P2 · 全局空格拦截阻断原生按钮操作

- 位置：`dist/js/input.js:55`。
- 浏览器复现：焦点置于开始按钮，Space后仍留在菜单，Return则正常开局。全局`keydown`无条件取消空格默认行为，没有排除按钮或浮层状态。
- 影响：开始、继续、帮助完成、选技等原生按钮的标准键盘激活受影响；鼠标和回车可用，故不属于无法启动。
- 建议：游戏移动/防滚动键仅在合适的战场上下文拦截，原生交互控件保留默认行为。DOM mock不模拟原生按钮默认激活，需补真实浏览器覆盖。

### A04 · P2 · 地刺受伤冷却离开范围后冻结

- 位置：`dist/js/combat.js:617`，尤其`:621`。
- 实测：2.8秒站在激活地刺上受击，HP280→272、计时0.65；离开后按60Hz连续推进240步，游戏时间约6.8秒，计时仍0.65；再次进入新激活周期，HP仍272、计时0.6333。
- 原因：冷却只在地刺激活且实体仍重叠时递减，离开范围或地刺收回都不流逝；该字段还跨地刺共享。
- 建议：统一按模拟时间递减，或记录绝对的下次可受伤时间；多个重叠地刺不能在一帧重复推进冷却。补离开/重新进入、地刺跨周期及重叠地刺用例。
- 注意：这是实际逐步推进的复现，不是跳变`game.time`而漏更新计时器。修复可能改变AI伤亡与竞技结果，应先解释差异再决定基线是否更新。

### A05 · P2 · 火球出生点可能嵌入实体墙

- 位置：`dist/js/combat.js:287`、`:545`；枪口偏移在`dist/js/balance.js:106`。
- 实测：真实庭院种子`audit-courtyard-0`，角色位于`(446.5788566,196.4134683)`，`blocked(actor)=false`；向右释放一级火球，中心直接前移15至`x=461.5788566`，半径10，`blocked(fireball)=true`。真实墙宽48，非只在自造薄墙才发生。
- 影响：贴墙释放时，投射物从非法几何位置开始，下一步碰撞会从墙内直接触发爆炸，影响位置、反馈与近墙目标判定。
- 建议：发射时扫掠角色至理想出生点的通道，并校验火球自身碰撞半径；受阻时将出生点限制在墙前合法空间。补正面/斜角贴墙及不同技能等级用例。
- 规则边界：爆炸范围是否应穿过障碍是另一个设计选择；本次仅确认出生点嵌墙，不将其扩大描述为火球无限穿墙或证明所有范围技能都应受墙遮挡。

### A06 · P2 · 竞技性能项只测量，没有失败阈值

- 位置：`tests/performance.js:44`、`tests/verify.mjs:69`。
- 证据：竞技性能脚本输出JSON后正常结束，没有检查P95或返回性能失败。使用合成时钟注入100ms/步后，脚本报告P95=100ms、占60Hz预算600%，仍退出0。
- 影响：未来即使竞技模拟严重变慢，该性能子项仍会被verify计为通过；当前本机实测本身很快，不能把注入值当作实际卡顿。
- 建议：为竞技性能设置有容差、可配置的预算与负载断言，超限返回非零；同时保存实际测量指标，而非只有脚本总运行时。首领对砍已有P95<8ms断言，应区分两者。另加真实浏览器帧耗时/长帧测量。

### A07 · P3 · 经验说明和版本速览没有完全同步

- 位置：`dist/index.html:39`、`:47`、`README.md:40`、`docs/HANDOFF.md:47`。
- 实际首领参战奖励已为4×1.5=6，但榜单说明和玩法指南仍写4，README也仍以5经验晶体说明；当前首领地图晶体实际为7.5。
- 交接文档顶部后续说明正确记录发布`2e4662a`，速览表的“已发布游戏逻辑提交”却仍指向`5440ad1`，容易使接手者误判当前版本。
- 建议：界面数值说明从配置生成；当前规则速览只维护一份，历史验收保留明确版本标签。上次经验调整确有文案遗漏，本轮如实记录，未静默修改。

### A08 · P3 · 地图晶体批量刷新会突破声明上限

- 位置：`dist/js/simulation.js:98`、`dist/js/boss-rules.js:114`。
- 实测：两个规则集都能在晶体数131、声明上限132时，一轮新增5颗达到136。
- 原因：只在批次开始前检查一次上限。掉落晶体另有生命周期，此处只评价地图批量补给的边界。
- 建议：补给数量限制为剩余容量，或每次地图刷新单独检查上限；定义上限是否包含战利品并写清。当前只多至多4颗，不能夸大成无界增长或已经引发内存泄漏。

## 优化顺序

1. **先修可靠性**：A01/A02优先，避免选错构筑和遮挡战场时继续运行；同轮处理空格、地刺计时和火球出生几何，再跑原回归及必要的首领整局。
2. **补验收缺口**：为上述边界加用例；本地DOM mock会自动创建任何查询到的ID，不能替代真实HTML、焦点、默认按键行为。保留快速mock，增加少量真实浏览器流程；仓库内目前没有CI配置，建议把常规verify放入提交检查，发布前运行首领矩阵。给首领增加少量确定性状态回归，原8局快照仅保护竞技庭院。
3. **把平衡反馈做细**：记录首次关键等级/满级时间、实际输出时长、死亡原因和每次复活损失。近战在这24局中输出总量更高且13冠，不能简单认定伤害不足；优先研究避招、危险提示和近战输出窗口，避免仅继续加伤。
4. **小步改善维护**：整理`renderer.js`和CSS的超长行，分离确有独立职责的代码；以状态哈希保护纯格式/结构改动。当前模拟P95不到1ms，没有证据支持为性能重写引擎或引入大型框架。渲染层每帧排序与分配可列入浏览器剖析候选，测出瓶颈后再优化。
5. **再做内容迭代**：可靠性和反馈完善后，再考虑少量能改变打法的构筑联动、首领招式变化；每次保留单一目标，避免同时大改经验、伤害、生命和AI后无法解释结果。
